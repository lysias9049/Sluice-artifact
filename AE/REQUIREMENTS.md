# Execution requirements

CPU-only. The historical v1.0.0 full N=2^23 workflow was tested by the authors on ARM64 Linux containers on an Apple Silicon host. Use 8 available logical CPUs, at least 24 GiB allocated to Docker/Linux, and at least 100 GiB free disk (SSD recommended); a 32 GiB or larger host is recommended. These are provisioning recommendations, not measured minima. Containers use at most 8 CPUs; the main prototype is predominantly single-threaded. Input generation uses a 22 GiB cap; proving uses 8 GiB (Full-RW and standard failure case) or 16 GiB (standard success case), with swap disabled. Generated inputs occupy 19.56 GiB combined. Full execution took approximately 5 hours 3 minutes, excluding build; allow additional time on other hardware. No GPU is required. An AE reviewer independently reproduced v1.0.0 on x86_64 Linux with native Docker 29.8, including the standard 12 GiB OOM and Full-RW 256 MiB sensitivity cases. This is reviewer-reported validation of v1.0.0, not an author-side x86_64 rerun of v1.0.1.

Docker with Linux containers and cgroup v2; host Python 3.9+; a POSIX shell for the optional install.sh helper. The Dockerfile uses Rust 1.96.0 on Debian Bookworm and installs Python 3, GNU time, and CA certificates. Cargo.lock pins Rust dependencies. Historical author-side Docker Engine: 29.5.2, Linux kernel 6.12.76-linuxkit, ARM64. Internet access is needed for initial image/dependency downloads; measurement containers run without networking. Docker permissions are required. No GUI, paid APIs, or API keys are required.

Disk headroom covers inputs, temporary streams, and build storage. Peak disk occupancy was not continuously measured. Cumulative read/write bytes are not disk capacity requirements. The reproduction takes under one day on the tested system; performance on other systems is not guaranteed.

For v1.0.1, measurement containers use the invoking host UID/GID. The image provides writable Cargo test caches inside the container. Linux inotify access to memory.max and memory.swap.max is required in addition to readable cgroup v2 limit files. Unavailable monitoring, detected file rewrites, changed limits, gaps longer than one second, and missing completion evidence invalidate a run. Use a new work directory if old root-owned files prevent access. The 100 ms monitor samples and file-write notifications are an operational check; they do not attest to arbitrary privileged host activity. See README.md and CHANGELOG.md for details and version-specific validation.
